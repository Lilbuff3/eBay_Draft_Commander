# Reliability & Tech-Debt — Design

**Date:** 2026-06-27
**Branch:** `docs/reliability-debt-plan`
**Status:** Validated design, ready for implementation planning

## Context

A review of the current codebase (13.3k LOC backend, 12k frontend) found a healthy,
working product with sound architecture and strong backend tests (515 test functions
across 62 files). The risk is operational debt and a few sharp edges, not design rot.

This design covers the **reliability / tech-debt** track, attacked in three sequenced
parts:

1. Fix the backend restart bug (real design — Approach A below)
2. Mechanical cleanup batch (dependency pins, prints→logger, branch prune, doc drift)
3. Frontend test foundation (coverage of the load-bearing paths)

Other tracks considered but deferred: revise-listing capability, profit features
(auto-offers / markdown scheduling), and throughput. They are out of scope here.

## Part 1 — Backend restart fix (supervisor wrapper)

### Root cause

`backend/app/blueprints/api/system_api.py` `/restart` calls:

```python
os.execv(sys.executable, [sys.executable] + sys.argv)
```

On Windows there is no real `fork`/`exec`; Python emulates `os.execv` via spawn + exit.
Combined with eventlet's monkey-patched socket bound to port 5000, the listening file
descriptor is not released before the replacement process tries to bind → **port 5000
left unbound**. The detached `pythonw backend/wsgi_service.py` launch makes it worse:
the re-exec'd child loses its detached/hidden context.

### Chosen approach — A: supervisor wrapper

A small, stable parent process launches the server as a disposable child. Only ever
one process binds port 5000, and the OS fully releases the port between child death and
respawn — structurally eliminating the bind race rather than papering over it.

Rejected alternatives:
- **B. Spawn-new-then-exit** — both processes want port 5000 at once; needs a
  handshake/retry-bind loop. This is essentially what fails today.
- **C. Kill-and-relaunch via PowerShell helper** — matches the current manual fix but
  adds an external script dependency, is Windows-only, and races on the kill→bind gap.

### Design

**New file: `backend/run_service.py`** (~40 lines, the stable parent):

```
set env DC_SUPERVISED=1
loop:
    child = Popen([sys.executable, "backend/wsgi_service.py"])
    code  = child.wait()
    if code == 42:  log "restart requested"; continue
    if code == 0:   log "clean stop"; break
    else:           crash → backoff + continue
                    (crash-loop guard: >3 crashes within 60s → give up)
on Ctrl-C / SIGTERM: terminate child, exit
```

**Exit-code contract:**

| Code | Meaning            | Supervisor action          |
|------|--------------------|----------------------------|
| 42   | Restart requested  | Relaunch child             |
| 0    | Clean stop         | Stop supervisor too        |
| other| Crash              | Relaunch (with guard)      |

**Endpoint change** (`system_api.py` `/restart`):

```python
if os.environ.get('DC_SUPERVISED'):
    # supervisor will relaunch; OS closes all FDs incl. port-5000 listener
    thread → sleep(1) → os._exit(42)
else:
    return 409, "Not supervised — launch via run_service.py to enable restart"
```

`os._exit(42)` skips Python-level cleanup, but the OS closes every file descriptor
(including the port-5000 listener) instantly. The supervisor then respawns into a clean
port. Child death fully releases the port *before* respawn — that is the whole fix.

**Launch changes:**

- Detached / prod: `Start-Process pythonw backend\run_service.py`
  (was `backend\wsgi_service.py`)
- Dev: `python backend/run_service.py` for restart capability, or keep
  `python backend/wsgi.py` for quick no-restart dev
- Child stays `backend/wsgi_service.py` unchanged (keeps its stdout/stderr redirect)

**Why robust:** only one process ever binds 5000; the supervisor is dumb and stable;
the app process is disposable.

### Verification

- Start via `run_service.py`; hit `POST /api/system/restart`; confirm `/api/system/health`
  returns 200 within a few seconds and port 5000 is bound by the new PID.
- Run `wsgi.py` directly (unsupervised); confirm `/restart` returns 409 and does not kill
  the process.
- Kill the child manually; confirm the supervisor relaunches it (crash path).

## Part 2 — Mechanical cleanup batch

Four sub-tasks. Two are blind-safe; two require triage (no blind `sed`/delete).

### 2a. Pin dependencies

`requirements.txt` has 11 deps, all `>=` (zero pins) — reproducibility risk
(rembg / onnxruntime / pillow / google-genai can float to breaking minors).

- Keep `requirements.txt` as top-level intent (`>=`).
- Add **`requirements.lock`** generated by `pip freeze` in the Python 3.12 venv.
- Document install as `pip install -r requirements.lock` for reproducible setups.

### 2b. prints → logger (triage, NOT blind)

62 `print()` calls across 14 files. Two classes:

- **Request-path / service prints** (jobs_api, queue_api, settings_api, listings_api,
  lookup_api, analytics_api, migration_api, ebay/auth.py) → convert to
  `get_logger().info/error`. These are the real bug — output is lost in production.
- **Genuine pre-logger bootstrap** (paths.py, core/logger.py, app/__init__.py, ui.py
  early boot) → leave or convert carefully; the logger may not exist yet.

Audit each occurrence; do not `sed` the lot.

### 2c. Prune branches (verify before delete)

~30 branches. Verified: only `feature/hermes-multi-photo` is unmerged into master.

- Bot noise `palette-*` (×10 remote) → delete (safe).
- Merged `feature/*` and `claude/*` → delete local + remote.
- `feature/hermes-multi-photo` (unmerged) → **confirm with owner first**; do not nuke
  unreviewed work.
- Keep `origin/archive/*` (intentional archive namespace).

### 2d. CLAUDE.md drift

CLAUDE.md says the API package has "7 sub-modules" — it actually has **8**
(`migration_api.py` is missing from the list). Also undocumented: `backend/mcp_server.py`
(read-only eBay MCP server).

- Add a `migration_api.py` entry (legacy active-listing import/scan).
- Add a `mcp_server.py` note.

**Order:** 2a → 2d (quick wins) then 2b → 2c (careful). Each its own commit.

## Part 3 — Frontend test foundation

Tooling is already installed (vitest, @testing-library/react, jest-dom, user-event,
jsdom, `src/test/setup.ts`). The gap is **coverage** — only 3 tests exist, two of which
are pure utils. Test by risk × ease; skip trivial leaf components (YAGNI).

### Phase A — pure / logic layer (biggest bang, lowest effort)

- `lib/api.ts` (412 lines, imported everywhere) — `vi.stubGlobal('fetch', vi.fn())`;
  test `apiFetch<T>` happy path, HTTP-error path, non-JSON/empty-body path. No MSW
  needed; vi mock is lighter for unit tests.
- `store/useCommanderStore.ts` (233 lines) — actions/selectors are near-pure; call them
  directly and assert state.
- `lib/sanitizer.ts` + `lib/utils.ts` — pure functions, trivial wins.

### Phase B — real-time

- `hooks/useJobSync.ts` — `vi.mock('socket.io-client')` returning a fake emitter; assert
  `job_added` / `job_update` / `job_log` mutate the store correctly. This is where silent
  production breakage hides.

### Phase C — highest-risk components (cap at 2–3)

- `listings/ReviewQueue.tsx` (guardrail-facing pending_review flow)
- `EditListingDialog.tsx` (mutates listings)
- Render + interact via `@testing-library/user-event`.

**Tooling add:** `@vitest/coverage-v8` + a `"test:coverage"` script. Set a **soft** floor
(~30%) and ratchet up over time. Do not hard-gate CI yet.

**Order:** A → B → C, each its own commit. Stop when the load-bearing paths are covered —
not at 100%.
